OTP Bypass and Username Enumeration in the Wild

Breaking authentication in an IT company's portal OTP bypass via packet manipulation, username enumeration through response timing, and what the app leaked in its error messages.

Background

This was a grey-box assessment on an internal employee portal for a mid-sized IT and BPM company. The application used a two-step login: first a username and password, then an OTP sent to the registered mobile number. On paper, that's a reasonable authentication flow. In practice, the implementation had three distinct flaws that together made the auth completely bypassable.

I'll walk through each one in the order I found them, because the sequence matters each finding opened the door to the next.

Finding 1 Username enumeration via response differences

The first thing I test on any login form is whether the application distinguishes between "wrong username" and "wrong password" either in the response message, status code, or timing. All three are information leaks.

I submitted a login request with a clearly non-existent username and captured the response in Burp Suite:

POST /auth/login HTTP/1.1
Host: portal.target.com
Content-Type: application/json

{ "username": "doesnotexist@company.com", "password": "test1234" }

HTTP/1.1 200 OK
{ "error": "User not found" }

Then with a valid username and wrong password:

{ "username": "valid.user@company.com", "password": "wrongpassword" }

HTTP/1.1 200 OK
{ "error": "Incorrect password" }

Two different error messages. The application was explicitly telling me which part of the credential pair was wrong. That's username enumeration I could now confirm whether any given email address had an account on the platform without needing the password.

Beyond the message content, the response times also differed. Valid usernames took ~320ms (the app was hitting a database and then a password hash comparison). Invalid usernames returned in ~40ms the query returned nothing, so no hash comparison ran. Even if the error messages had been identical, timing alone would have been enough.

Finding 2 Information leakage in error responses

While mapping the application further, I noticed the error responses were more verbose than they needed to be. On certain failed requests, the API was returning internal field names, partial stack traces, and in one case a response body that included the user's registered phone number in masked form ******7823 before the OTP step had even been reached.

That masked number was enough to confirm account ownership and, combined with the enumeration finding, meant an attacker could map usernames to partial phone numbers without ever authenticating. For a social engineering or SIM-swap scenario, that's a meaningful starting point.

The broader issue here was that the application had no consistent error handling layer. Each endpoint was returning whatever the backend threw, unfiltered.

Finding 3 OTP bypass via packet manipulation

This was the critical finding. After entering valid credentials, the application sent an OTP to the user's registered mobile number and redirected to a verification screen. The request to verify the OTP looked like this:

POST /auth/verify-otp HTTP/1.1
Host: portal.target.com
Content-Type: application/json
Authorization: Bearer <pre-auth-session-token>

{
  "username": "valid.user@company.com",
  "otp": "482610",
  "otp_verified": false
}

The field that caught my attention was "otp_verified": false. The client was sending the verification status to the server and the server was trusting it. I intercepted the request in Burp Suite and changed that single field:

{
  "username": "valid.user@company.com",
  "otp": "000000",
  "otp_verified": true
}

The OTP value itself was wrong. It didn't matter. The server read otp_verified: true, skipped its own validation logic, and issued a fully authenticated session token.

The OTP the entire second factor was nullified by changing one boolean in the request body.

Why this happens

This is a classic case of trusting client-supplied state. The server should be the sole authority on whether an OTP has been verified. The verification result should never travel from client to server it should be computed server-side and stored in a server-side session. Sending otp_verified in the request body is the equivalent of asking the user to mark their own exam papers.

The likely explanation is that the OTP verification was originally handled client-side (a common shortcut in early-stage development), and when server-side verification was added, the old field was never removed and the server-side check was never made authoritative.

Combined impact

Chaining all three findings: an attacker could enumerate valid usernames via error messages, identify accounts of interest, enter those credentials (or brute-force the password there was no rate limiting), and then bypass the OTP entirely via the otp_verified manipulation. Full account takeover, no SMS access required.

Remediation

  • Uniform error messages: Return the same message for invalid username and invalid password something generic like "Incorrect credentials." Never distinguish between the two.
  • Consistent response timing: Artificially pad responses to a fixed duration so timing attacks don't reveal whether a username exists.
  • Server-side OTP state only: Remove otp_verified from the client request entirely. The server generates the OTP, stores a hashed version in the session, and validates the submitted value against that stored hash. The client has no say in the outcome.
  • Centralised error handling: All API errors should pass through a single error handler that strips internal details before responding. Log the full error server-side, return only a safe, generic message to the client.
  • Rate limiting on auth endpoints: Both the login and OTP endpoints should enforce rate limiting and lockout after a threshold of failed attempts.

Key takeaway

Authentication bugs rarely exist in isolation. The OTP bypass here was severe on its own but it was the enumeration finding that made targeting specific accounts possible. When you're testing auth flows, map every request in the sequence before you start manipulating anything. The interesting field is often not in the obvious place.
