Exploiting IDOR in a GraphQL API

A walkthrough of finding and exploiting an Insecure Direct Object Reference in a hotel industry GraphQL endpoint no credentials needed to access other users' profiles.

Background

During a web application penetration test for a client in the hospitality sector, I came across a GraphQL API powering their guest-facing portal. GraphQL is increasingly common in modern apps, and it introduces a specific class of access control risks that traditional REST testing doesn't always catch. This engagement was a good reminder of why you treat every API type on its own terms.

The application allowed registered guests to view their own booking details, loyalty points, and personal profile. My goal was to test whether the authorization model actually enforced those boundaries or just trusted what the client sent.

Reconnaissance: Introspection is your friend

The first thing I do with any GraphQL endpoint is check whether introspection is enabled. Many production deployments leave it on, which hands you the entire schema every type, query, mutation, and field without needing access to source code.

POST /graphql HTTP/1.1
Host: target-hotel-app.com
Content-Type: application/json

{
  "query": "{ __schema { types { name fields { name } } } }"
}

Introspection was enabled. The schema came back in full. I piped it through GraphQL Voyager to visualise the relationships, which immediately surfaced a getGuestProfile query that accepted a guestId argument.

Identifying the vulnerable query

The query looked like this in the schema:

type Query {
  getGuestProfile(guestId: ID!): GuestProfile
}

type GuestProfile {
  id: ID
  fullName: String
  email: String
  phone: String
  loyaltyPoints: Int
  bookingHistory: [Booking]
}

A query that takes a user-supplied ID and returns a profile with no visible authorization logic in the schema. The question was whether that logic existed server-side. Spoiler: it didn't.

I authenticated as a test guest account and captured my own guestId from the response it was a sequential integer. 1042.

Exploiting the IDOR

I sent the same getGuestProfile query with a modified ID:

POST /graphql HTTP/1.1
Host: target-hotel-app.com
Content-Type: application/json
Authorization: Bearer <my_valid_token>

{
  "query": "{ getGuestProfile(guestId: \"1041\") {
    id
    fullName
    email
    phone
    loyaltyPoints
    bookingHistory { checkIn checkOut roomType }
  }}"
}

The server returned another guest's full profile name, email, phone number, booking history without any error or access denied response. My authenticated session had no relation to guest 1041. The API simply returned whoever I asked for.

I iterated across a small range (1038–1045) to confirm it wasn't a one-off. Every request returned a valid profile belonging to a different registered guest.

Why GraphQL makes this easy to miss

In a REST API, access control is typically applied at the route level GET /users/1041 can be restricted by middleware before the controller even runs. In GraphQL, there's a single endpoint (/graphql) and a single resolver function per field. Authorization has to be explicitly implemented inside each resolver, or via a dedicated middleware layer like GraphQL Shield.

Many development teams build the data layer first and treat auth as something to layer on later. In GraphQL, "later" often never comes especially for internal or seemingly low-risk queries.

Impact

The exposed data included full names, email addresses, phone numbers, and complete booking histories with room types and dates. For a hospitality application, that's sensitive PII and booking history specifically can reveal details guests reasonably expect to be private. The sequential ID scheme made mass enumeration trivial; a script could have harvested every guest profile in the database in minutes.

Remediation

The fix requires changes at two levels:

  • Resolver-level authorization: Every resolver that returns user-specific data should compare the requested resource ID against the authenticated user's identity. If they don't match, return a permission error not the data.
  • Non-sequential IDs: Replace integer IDs with UUIDs or other non-enumerable identifiers. This doesn't fix broken access control, but it eliminates the trivial enumeration path and reduces the blast radius of any future IDOR.
  • Disable introspection in production: Introspection is a development convenience, not a production requirement. Disabling it doesn't prevent exploitation if an attacker has the query names but it removes the easy schema discovery step.

Key takeaway

GraphQL IDORs are underreported not because they're rare, but because REST-focused testers often treat /graphql as a black box. Always request the schema first. Look for any query or mutation that accepts an ID argument. Then test whether the server enforces that only the authenticated user can access their own resources because the schema certainly won't do it for you.
