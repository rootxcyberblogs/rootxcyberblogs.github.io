Google Dorking for Recon: Finding What Shouldn't Be Public

During an engagement with an adhesive manufacturing company, Google dorking surfaced a vendor table with PII — directly accessible without authentication. A practical guide to structured recon.

Why recon matters more than most testers admit

There's a tendency in penetration testing to rush toward the active phase — scanning, fuzzing, probing. Recon gets treated as a checkbox rather than a discipline. That's a mistake. Some of the most severe findings I've come across required no exploitation at all — just the patience to look at what was already publicly visible before touching a single endpoint.

This engagement is a good example. The client was an adhesive manufacturing company. Not a fintech, not a healthcare provider — a manufacturing business. The assumption from their side was that their web presence was low-risk. What Google had indexed told a different story.

What is Google dorking?

Google dorking — also called Google hacking — is the use of advanced search operators to find information that Google has indexed but that organisations didn't intend to expose publicly. The underlying mechanism is simple: Google crawls everything it can reach. If a page or file is publicly accessible and not explicitly excluded via robots.txt or meta tags, it gets indexed. The data is already out there — dorking just surfaces it systematically.

The core operators worth knowing:

site:          restrict results to a specific domain
               site:target.com

inurl:         match text in the URL itself
               inurl:admin

intitle:       match text in the page title
               intitle:"index of"

filetype:      filter by file extension
               filetype:pdf

ext:           same as filetype, sometimes more reliable
               ext:xlsx

intext:        match text within the page body
               intext:"confidential"

cache:         view Google's cached version of a page
               cache:target.com/page

These operators combine. That's where the power is.

The engagement: structured recon on a manufacturing domain

Before touching the client's infrastructure, I ran a passive recon phase entirely through Google — no direct requests to their servers, nothing that would show up in their logs. The goal was to understand the surface area: subdomains indexed, file types exposed, pages that shouldn't be crawlable.

I started broad and narrowed down:

site:target-manufacturer.com

This returned their main site, a few product pages, and — unexpectedly — a subdomain I hadn't seen in the initial scope brief. A vendor portal, apparently running a separate application.

site:vendors.target-manufacturer.com

A handful of results. Most were login pages and marketing PDFs. One result stood out: a URL with a path that looked like a direct database view — /vendors.target-manufacturer.com/reports/vendor_table?export=true. The page title in the search result read "Vendor Directory — All Records."

The finding: a vendor table behind no authentication

I opened the URL. No redirect to a login page. No session check. The page loaded immediately and rendered a full HTML table — vendor company names, contact persons, email addresses, phone numbers, and physical addresses. Hundreds of records. All of it PII belonging to the client's supplier network.

The page had an export=true parameter in the URL. I tried export=csv — it returned the entire dataset as a downloadable CSV file, still without any authentication prompt.

The URL structure suggested this was a reporting view generated by a backend admin tool — something likely intended for internal use only, perhaps shared with a vendor manager via a direct link at some point. At some stage, the path had become crawlable. Google indexed it. It had been sitting there, publicly accessible, for who knows how long.

Extending the dork: what else was out there

Once I had a confirmed finding on the vendor subdomain, I widened the search to see what else the domain family was leaking:

site:target-manufacturer.com filetype:xlsx
site:target-manufacturer.com filetype:pdf "confidential"
site:target-manufacturer.com inurl:report
site:target-manufacturer.com inurl:backup
site:target-manufacturer.com intitle:"index of"

The intitle:"index of" dork is particularly useful — it finds open directory listings where the web server is serving file trees without an index page. In this case it returned nothing, but it's worth running on every engagement. Exposed backup files (.bak, .sql, .old) and configuration files (.env, config.php) are among the most damaging findings in this category and they surface regularly.

A few additional operators I use as standard:

site:target.com ext:env
site:target.com ext:sql
site:target.com ext:log
site:target.com inurl:".git"
site:target.com inurl:wp-config
site:target.com intext:"API_KEY" OR intext:"api_key"

Tools that extend passive recon beyond Google

Google dorking is a starting point, not the whole picture. I pair it with a few other passive sources during recon:

  • Shodan — indexes internet-facing devices and services. Useful for finding exposed ports, service banners, and infrastructure that isn't part of the web application but is still in scope. A query like org:"Target Company" often surfaces servers the client forgot about.
  • Wayback Machine (web.archive.org) — cached historical versions of pages. Useful when a sensitive URL has since been taken down — the content may still be in the archive. Also useful for finding old API endpoints that were deprecated but never properly removed from the live application.
  • Amass / Sublist3r — subdomain enumeration. Google's site: operator finds what's indexed; these tools find what's resolvable. The vendor portal subdomain in this engagement would have appeared in Amass results even if Google hadn't indexed any pages on it.
  • Maltego — relationship mapping. Connects domains, IPs, email addresses, and organisational data into a visual graph. Most useful when you need to understand a complex organisation's external footprint before scoping the active phase.

Impact

The vendor table exposure was rated high severity. The data included full contact details for the client's entire supplier network — a dataset that a competitor or bad actor could use for targeted phishing, business email compromise, or simply selling. The client had no visibility that the page was publicly accessible. They assumed that because it "required a link to access," it was protected. Security by obscurity is not access control.

Remediation

  • Authentication on every internal view: Any page that renders business data should sit behind a session check, regardless of how it's accessed. Direct links are not a substitute for auth.
  • robots.txt and noindex tags: Add Disallow rules in robots.txt for any path that shouldn't be crawled, and include <meta name="robots" content="noindex"> on sensitive pages. Note — this is a crawl instruction, not access control. It reduces exposure but doesn't replace authentication.
  • Regular Google dork audits: Run a site: search on your own domain periodically. If you find something unexpected in the results, so can an attacker. This takes ten minutes and catches a class of exposure that no internal scanner will find.
  • Remove export parameters from unauthenticated routes: The export=csv parameter compounded the issue significantly. Data export functionality must always require authentication and, where appropriate, audit logging.

Key takeaway

The most uncomfortable finding you can deliver to a client is one where the data was already public — not because of a technical exploit, but because nobody checked. Google dorking costs nothing, requires no special tooling, and produces findings that are immediately understandable to non-technical stakeholders. Run it on every engagement, and run it on your own organisation too.
