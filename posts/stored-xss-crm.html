Stored XSS in a CRM Portal: From Notes Field to UI Defacement

How injecting a payload into a seemingly innocuous notes field in a quick-commerce CRM caused full defacement of the user interface and why stored XSS is still underestimated.

The underestimation problem

Cross-site scripting has been on the OWASP Top 10 for over two decades. Developers know the name. Security awareness training mentions it. And yet, in practice, XSS findings particularly stored XSS are still frequently triaged as medium or low severity by development teams who've internalised a shallow version of what the vulnerability does. "It just shows an alert box" is the most dangerous sentence in web security.

This engagement changed how at least one team thought about it. The client was a quick-commerce company a fast-delivery startup with an internal CRM used by their operations and delivery management teams. The notes field was there to let agents leave comments on customer orders. It was never meant to be a vector for anything.

Finding the injection point

My approach to XSS testing on any application with text input is methodical I don't immediately throw payloads. I first observe how the application handles input: does it reflect it immediately, store it and render later, pass it to another user's view, or send it in emails or notifications? The rendering context determines the payload and, more importantly, the real-world impact.

In the CRM, the notes field on an order record accepted free text and stored it. When any agent opened that order record, the note was rendered in the order detail panel. That's the key characteristic of stored XSS: the payload executes in the browser of every user who views the affected page not just the person who submitted it.

I started with a basic probe to check whether output was being encoded:

<script>alert(1)</script>

No execution the script tags appeared as literal text in the rendered note. The application was stripping or encoding <script> tags. That's a common partial fix and a common false finish line for developers. The input was still injectable; only one vector was blocked.

Bypassing the filter

When <script> tags are filtered, the next step is testing event-handler injection HTML attributes that execute JavaScript without needing a script element:

<img src=x onerror=alert(1)>

The image tag rendered. The src=x triggered a failed load. The onerror handler fired. The alert executed.

The filter was blocking script tags specifically a blocklist approach rather than a proper output encoding or allowlist approach. Any HTML tag with a JavaScript event handler bypassed it entirely. This is a textbook example of why blocklist-based XSS filters consistently fail: the attack surface is too large to enumerate. There are dozens of HTML elements and hundreds of event attributes that can carry JavaScript. You can't block them all reliably.

Escalating to UI defacement

An alert box confirms execution it's a PoC, nothing more. To demonstrate real impact to the client, I escalated to a payload that showed what an attacker could actually do with arbitrary JavaScript execution in an authenticated agent's browser session.

The defacement payload replaced the entire content of the order detail panel with attacker-controlled HTML:

<img src=x onerror="
  document.body.innerHTML = '<div style=\'
    position:fixed;top:0;left:0;width:100%;height:100%;
    background:#111;display:flex;align-items:center;
    justify-content:center;z-index:9999;
  \'><h1 style=\'color:#fff;font-family:monospace\'>
    [Defaced  XSS PoC by ]
  </h1></div>'
">

When any agent opened the affected order record, their entire CRM view was replaced. The legitimate interface was gone. Every element navigation, order data, action buttons was wiped and replaced with the injected content.

The payload was stored in the database. Every agent who loaded that order saw the defacement. It persisted until the note was deleted.

What an attacker would actually do

Defacement is a demonstrative PoC it's visually convincing for a report but not what a malicious actor would deploy. With the same injection point, a real attacker has several more damaging options:

  • Session token theft: document.cookie can be exfiltrated to an attacker-controlled server via a fetch or image request. Any agent who views the page loses their session the attacker can then replay that token and operate as that agent inside the CRM.
  • Credential harvesting: An overlay mimicking a login prompt ("Your session has expired please log in again") can capture credentials from agents who don't notice the URL hasn't changed.
  • Keylogging: document.addEventListener('keydown', ...) captures everything typed while the injected script is active including passwords entered into other fields on the page.
  • Internal recon: JavaScript running in an authenticated session can make authenticated API requests, enumerate internal endpoints, and exfiltrate data that would otherwise require credentials to access.

The notes field looked low-risk. In an internal CRM used by operations staff, it was a direct path to every authenticated session that touched an affected order record.

Why CRM applications are high-value XSS targets

CRMs and internal operations tools are often deprioritised in security reviews because they're "internal." But internal doesn't mean low-risk it often means the opposite. These applications typically:

  • Hold customer PII at scale
  • Are accessed by large numbers of staff with varying security awareness
  • Have broad permissions an agent's session can do a lot
  • Were built under speed pressure, with security as an afterthought
  • Receive fewer penetration tests than customer-facing applications

A stored XSS in a customer-facing app affects whoever visits a public page. A stored XSS in an internal CRM affects authenticated staff people whose sessions have real access to real data and real actions.

Remediation

  • Output encoding, not input filtering: The correct fix for XSS is encoding output at render time, not stripping input on the way in. Use your framework's built-in templating engine with auto-escaping enabled React, Angular, and Django templates all handle this by default if you don't bypass them. If the notes field renders as text, encode all HTML entities: & → &amp;, < → &lt;, and so on.
  • Content Security Policy (CSP): A properly configured CSP header restricts what scripts can execute and where data can be sent. A strict policy (script-src 'self', no unsafe-inline) would have prevented the onerror handler from executing entirely, even with the injection present. CSP is a defence-in-depth measure it doesn't replace encoding, but it substantially raises the bar for exploitation.
  • HttpOnly cookies: Set the HttpOnly flag on session cookies. This prevents document.cookie access from JavaScript, which blocks the most common XSS-to-session-theft path. It doesn't stop all XSS impact, but it removes the easiest escalation route.
  • Rich text sanitisation: If the notes field genuinely needs to support formatting (bold, links), use a server-side HTML sanitisation library DOMPurify on the client, or Bleach in Python with a strict allowlist of permitted tags and attributes. Never use a custom blocklist.

Key takeaway

Stored XSS in an internal tool is not a low-severity finding. The severity of XSS is determined by what the injected script can do in the context of the affected session and in a CRM used by operations staff, that context is significant. If you're triaging XSS findings on internal applications, think past the alert box. Think about what an authenticated session in that application is capable of, and ask whether arbitrary JavaScript execution in that context is really a medium.
